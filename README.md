# RESTful Shakespeare client

A minimal client of the RESTful Shakespeare API (the `restful-shakespeare3-openapi`
project), generated from its OpenAPI description with
[OpenAPI Generator](https://openapi-generator.tech/). The project shows that client
code can be generated from an OpenAPI description, and also the limits of such
generated code.

## Running

1. Start the server: `mvn spring-boot:run` in the `restful-shakespeare3-openapi`
   project (on port 8080).
2. Run the client in this project:

   ```
   mvn compile exec:java
   ```

The client gets a scene, bookmarks it as `alice`, deletes the bookmark, and finally
requests a nonexistent play:

```
GET a scene: 200 OK
  Link: </plays/macbeth/acts/1/scenes/1>; rel="self"
  ...
  <SCENE><TITLE>SCENE I.  A desert place.</TITLE>...
POST a bookmark: 201 CREATED, Location: /users/alice/bookmarks/1
  <bookmark id="1"><target>/plays/macbeth/acts/1/scenes/1</target><note>The witches</note></bookmark>
DELETE the bookmark: 204 NO_CONTENT
GET a nonexistent play: 404 NOT_FOUND
  <problem xmlns="urn:ietf:rfc:7807">...
```

## How it works

* `openapi/openapi.yaml`: an unchanged copy of the OpenAPI description of the server
  (`openapi/openapi.yaml` of `restful-shakespeare3-openapi`).
* `openapi/openapi-3.1.yaml`: the input of the generator, an OpenAPI 3.1 version of
  the description (see below).
* `pom.xml`: the `generate` goal of `openapi-generator-maven-plugin` runs in the
  `generate-sources` phase, before compiling. It generates the client code into
  `target/generated-sources/openapi/src/main/java`, and adds this folder to the
  sources to compile. So the generated code is not part of the project, it is
  regenerated by every build: look at it in the `target` folder.
* The generated code consists of two Java interfaces, one per tag (controller) of
  the description: `PlayControllerApi` and `BookmarkControllerApi` in the
  `hu.unideb.inf.shakespeare.client.api` package. These are
  [Spring HTTP interfaces](https://docs.spring.io/spring-framework/reference/integration/rest-clients.html#rest-http-interface):
  the `@HttpExchange` annotations of their methods give the method, the URI
  template and the media types of the requests. For example:

  ```java
  /**
   * GET /plays/{play}/acts/{act}/scenes/{scene} : Returns a scene of an act
   * ...
   */
  @HttpExchange(
      method = "GET",
      value = PlayControllerApi.PATH_SCENE,
      accept = { "application/problem+xml", "application/xml" }
  )
  ResponseEntity<String> scene(
       @PathVariable("play") String play,
       @PathVariable("act") Integer act,
       @PathVariable("scene") Integer scene
  );
  ```

  The names of the methods are the `operationId`s, and their Javadoc comments come
  from the descriptions of the operations, parameters and responses.
* Spring implements the interfaces at runtime: `HttpServiceProxyFactory` creates
  objects that send the requests with a `RestClient` (see `App.java`). This needs
  only the `spring-web` and `spring-context` modules, not Spring Boot.

## OpenAPI 3.2

OpenAPI Generator (7.27.0) does not support OpenAPI 3.2 yet: its parser
(swagger-parser) only recognizes OpenAPI 3.0 and 3.1 descriptions. Given the
`openapi: 3.2.0` description, it does not recognize the document at all, tries the
older Swagger formats, and fails with a long list of misleading errors (e.g.,
`attribute paths.'/plays'(get).responses.200.content is unexpected`). So the
generator gets an OpenAPI 3.1 version of the description, with two changes:

* `openapi: 3.1.0` instead of `openapi: 3.2.0`;
* the `query` fields of the path items (the `QUERY` operations) are removed, since
  OpenAPI 3.1 has no such field. So there is no client code for the `QUERY`
  operations.

When the description of the server changes, copy it to `openapi/openapi.yaml`, and
make these changes again, by hand or, e.g., with [yq](https://github.com/mikefarah/yq):

```
yq '.openapi = "3.1.0" | del(.paths[].query)' openapi/openapi.yaml > openapi/openapi-3.1.yaml
```

The plugin skips the validation of the description (`skipValidateSpec`), because the
parser reports a false error: `attribute info.license.identifier is missing`.
OpenAPI 3.1 does not require the `identifier` (or the `url`) of a license, only
its `name`.

## What to notice

* **The representations are strings.** The description gives the schema of the
  XML representations as `type: string` only, so the methods return
  `ResponseEntity<String>`, and there are no model classes. The generated code is
  only as detailed as the description: with schemas for the representations, the
  generator would generate classes for them too.
* **Hypermedia is not used.** The URI templates are hard-coded in the generated
  interfaces (the `PATH_...` constants), and the client ignores the links of the
  `Link` header fields. To delete the new bookmark, the client even has to take
  the URI in the `Location` header field apart, since the generated method needs
  the user and the identifier of the bookmark. This is exactly the coupling that
  HATEOAS avoids: if the server changed its URIs, a client following the links
  would keep working, while the generated client would have to be regenerated.
* **Authentication is not generated.** The description says which operations need
  HTTP Basic authentication, but the generated interfaces do not use it: the
  client sends the credentials with every request (see `App.java`).
* **Errors are exceptions.** Error responses are thrown as
  `HttpClientErrorException` (4xx) and `HttpServerErrorException` (5xx), and the
  problem details are just a string in the exception.
* **No `QUERY`** (see above).

## Other generators

OpenAPI Generator supports many other languages and libraries
(`npx @openapitools/openapi-generator-cli list`), e.g.:

```
npx @openapitools/openapi-generator-cli generate -i openapi/openapi-3.1.yaml \
  -g typescript-fetch -o target/typescript-client --skip-validate-spec
```

A good exercise is to try `-g java --library native` (a client built on the
`java.net.http` package of the JDK): the generated code reads every response body
with Jackson, as JSON, so it cannot handle the XML representations of this API.
